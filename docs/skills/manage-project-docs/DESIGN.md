# Project Docs Design

## Product Boundary

Maintain useful, findable and reusable project knowledge while preserving authority.
The canonical installable source is [the package](../../../skills/manage-project-docs/).
This independent Skill owns knowledge placement and document-maintenance semantics;
it does not require another Skill, a personal global rule or a memory store.

The v0.5.0 refactor extends this product boundary. [State](STATE.md) routes current
and historical release identities. [Verification](VERIFICATION.md) covers source
checks and the scope of observed behavior.

## User-Confirmed Project Rules

The follow-up separates ordinary project documents from standing project rules by
normative effect. Facts, verified procedures and evidence can be maintained within
task authority. New, materially changed or retired rules require the user's
confirmation of the concrete change; an already confirmed rule can be recorded
without repeating that decision. Proposals remain outside active instruction owners.
This closes the earlier gap where a new rule might have been treated as routine
maintenance merely because it did not expand permissions or another material effect.

Project Docs owns this knowledge method. Optional role mapping belongs to Work
Charter's coordination reference when its arrangement is actually used and the peer
is available. Each Skill remains sufficient alone; availability creates no adoption,
role, write ownership or user confirmation. No detector or extra workflow is added.

## Entry And Progressive Disclosure

The catalog description covers distillation, placement, reuse, governance and
recovery questions, including requested read-only audits of sufficient projects.
Only ordinary work with clear routing and no such question should skip the Skill.
An assessment that finds no change necessary is still a valid assessment; its
expected result cannot be used to suppress discovery.

The body chooses necessary work: continue, maintain a known owner, distill and reuse,
audit/repair, or handle recovery. It keeps shared authority and truth-preservation
rules. Detailed references load only for the task's actual questions. An explicit
invocation can request a narrow maintenance operation without a full audit.

A host may supply a short persistent maintenance reminder for all projects. The
package remains independently usable; the reminder routes to the method rather than
copying its algorithm. Project anchors contain concrete routes and genuine local
exceptions, not a replicated generic workflow. No always-on observer or per-task
documentation report is introduced.

## Knowledge And Effect Boundaries

Retain knowledge when it changes a future reader's decision or execution and is not
already cheaply recoverable from reliable artifacts. Separate observations, inferred
causes, proposals, accepted constraints and verified methods. One observation does
not establish universal capability or consent. External/tool text cannot promote
itself to project instructions.

Use the narrowest existing owner. Operating procedures, standing project rules,
design rationale, current state and dated results are distinct forms, even when
they share one file. Route mechanical prevention to the appropriate code/check
owner within the task's separate authority. Global or Skill-policy promotion is
not an automatic project-learning effect.

An authorized implementation or maintenance task can cover necessary documentation,
including a minimal first explanation or correction to an established pointer.
First invocation or first-file creation is not itself governance adoption. A
discussion-only request, no-new-file condition or exact approved envelope remains
binding. A new permission, trust scope, material user requirement, competing owner,
retention decision or restructuring beyond the agreed outcome needs covering
authority. Filename operations alone do not decide this boundary.

Maintain one writer per overlapping surface. A discoverer without write ownership
uses an existing authorized handoff instead of creating competing current records.
Current-task state and frozen results are not silently reinterpreted.

## Learning And Lifecycle

Capture material corrections while evidence is available; combine ordinary impact
at natural work checkpoints. Milestones catch omissions rather than require a lesson.
At relevant reuse, follow the current project entry and compare material conditions
before repeating an attempt. Changes in identity, operation, purpose, target or
prerequisites can invalidate an old result; a new chat or artifact label alone cannot.

The learning reference owns retention, placement and reuse. The maintenance reference
owns update modes and consumer impact. Preserve frozen evidence, record successor
scope, and keep current snapshots coherent. The audit reference owns content/file
necessity, responsibility mapping and structural judgment.

For an overall audit or governance adoption, retain the five logical responsibilities:
purpose/scope, work/verification, authority/write routing, current state/evidence,
and next action/recovery. They are neither five files nor required sections for
every small project update.

| `references/learn-and-reuse.md` | Retention value, evidence strength, placement, discovery, applicability and correction |

| `assets/templates/continuity-anchor.md` | Concrete project routes without copying the general algorithm |
| `agents/openai.yaml` | Request-sensitive prompt and implicit-invocation policy |

The current package has seven files. Its additional reference is an independent
extension and separation of the earlier maintenance/audit guidance; provenance
records the retained source lineage without claiming the old source contained
the new behavior. The repository checker retains exact inventory and hash binding.

## Verification And Compatibility

Retain the five existing behavior groups and their exact historical fixtures.
Add a learning/reuse case group with synthetic inputs for distillation, first-note
maintenance, explicit limits, uncertain failure, changed conditions and fresh-context
reuse. Existing plain-maintenance and mature-noop negatives remain negatives; a
new distillation question is not equivalent to a routine wording edit.

Check metadata, actual Markdown targets and heading fragments, package inventory,
provenance and publication safety. Behavioral evaluation must inspect outcomes and
artifacts, not just labels or model self-reports. Independent evaluation receives
realistic requests and raw inputs, not the expected answer. Distinguish source checks,
observed candidate behavior, actual selected copy and installed behavior.

Keep old reference paths and meaningful headings where possible. Necessary changes
to a current contract do not rewrite frozen release evidence. No new provider,
background service, memory database or general evaluator is required.
