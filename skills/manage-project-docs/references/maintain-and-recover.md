# Maintain And Recover

Use this branch for current-entry maintenance, lifecycle and recovery.

## Current Entry

An active status/recovery document opens with the user's outcome reached, the
current blocker and the next action. The summary is at most 300 Unicode code points
including spaces and line breaks, and at most 6 non-empty logical lines.

Keep current constraints, unresolved effects, writer and next action in a coherent
snapshot. Move completed attempts and superseded narrative to the existing linked
history/evidence owner, grouped by event or phase. Preserve frozen records intact
and link them from the current entry. Use short identifiers in narrative and full
hashes in linked receipts. Update the snapshot when the outcome, blocker or next
action changes.

## Maintain Existing Owners

For an affected fact, locate the rule/method/state/evidence owner and its actual
consumers, including necessary unchanged ones. Use task authority for ordinary
updates and [rule confirmation](../SKILL.md#project-rule-confirmation) for standing
rules. Reuse valid checks, update owner and links together, and verify changed
meaning, applicability and the next reader's route.

## Learning And Reuse Events

Use [Learn And Reuse](learn-and-reuse.md) for retention and placement judgments.
Catch material omissions at useful checkpoints; verify relevant conditions when
reusing a method. The assigned writer maintains shared facts.

## Choose Update Modes By Content

| Content | Update |
|---|---|
| Current state | Replace a coherent snapshot when result/blocker/next action changes |
| Accepted rule or contract | Revise within the confirmed change and retain rationale |
| Frozen evidence or decision history | Preserve it and link a successor/correction |
| Generated view | Update its true source and regenerate |

State which scope is superseded, invalidated or still applicable. Current approval,
implementation and verification remain distinct facts.

## Mixed Document Examples

README can contain usage, current rules and historical notes with different update
modes. STATE holds the current snapshot; evidence and decisions retain dated
records. HANDOFF links current recovery and historical proof. Published release
records stay frozen while current provenance is updated for a new candidate.

## Keep Recovery State Coherent

Make goal, current result, writer, blocker and next action describe one checkpoint.
Resolve material contradictions at their existing owners before the dependent
action. Report the precise continuity gap if authority or evidence is missing.

## Maintain The Continuity Anchor

Maintain concrete start/recovery/method routes and genuine local exceptions in
the project's existing entry. Refresh broken links to the same owner directly;
a different ownership or authority choice follows its decision.
Report continuity as strong only when the entry, evidence and required owners
support the actual next step; otherwise identify the weak link.

## Pause And Handoff

At the authorized current owner preserve the goal, completed/remaining work,
workspace/writer state, evidence, blocker and next action. Keep the full history
at its original location and link it from the short entry.

## Recover

Read the project's current entry and necessary sources. Check scope, actual
checkout/baseline, dirty ownership and the last relevant checkpoint against live
state. Resume the covered next action and preserve still-unresolved effects.

## Completion Report

After the update, check actual files and affected consumers, including generated
or untracked artifacts. Report observed changes and gaps; distinguish source,
installed state, actual loading and reuse. Use the normal delivery rather than
a separate maintenance report.
