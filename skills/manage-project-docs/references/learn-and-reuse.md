# Learn And Reuse

Use this branch for knowledge whose retention or next use needs judgment.
Authorization and standing-rule decisions follow [the Skill entry](../SKILL.md).

## Recognize A Useful Event

Consider a material user correction, verified reusable method, missed precedent,
changed prerequisite or contradicted lesson. Retain a necessary operating
prerequisite before delivery; combine ordinary notes at meaningful checkpoints.
Start with current evidence and known project sources, expanding only to resolve
a concrete question.

## Decide Whether To Retain It

Keep a lesson that changes a future decision and is not already cheaply recoverable.
Consider reuse, recurrence, non-obvious conditions and maintenance cost. Improve
an existing equivalent statement or discovery link first. When the current
artifacts suffice, continue without another note.

Separate observation, inference, proposal, accepted decision and verified method.
A failure records its conditions; a success is reused only where its relevant
identity, operation, purpose, target and prerequisites match.
Resource trust is recorded with its user-confirmed scope, separately from
operational capability and action authorization.

## Choose The Narrowest Useful Form

| Knowledge | Owner |
|---|---|
| Already explicit in reliable artifacts | That artifact and any necessary entry link |
| Repeatable method/prerequisites | Existing README/runbook/deployment/verification guide |
| Proposed standing requirement | Existing proposal/decision record until user confirmation |
| Accepted constraint | Current rule owner after [confirmation](../SKILL.md#project-rule-confirmation) |
| Tradeoff/rationale | Existing design/decision record |
| Bounded result, failure or current uncertainty | Current state/issue/evidence owner |
| Mechanical prevention | Code/check/test owner within its authority |
| Cross-project idea | Proposal to the appropriate shared owner |

Detailed procedures stay at their operational owner. Use the nearest project
scope. A project Skill is appropriate only for a concrete recurring workflow
that benefits from separate packaging.

## Preserve Enough To Reuse

Record the trigger, relevant conditions, supported method/conclusion, source or
decision locator and reassessment trigger. Choose the smallest useful prose.
Use real identities only where authorized and necessary; synthetic examples stay
clearly synthetic. Source checks, installed state and actual outcomes have their
own evidence. Handle uncertain effects through the actual task's recovery contract.

## Connect The Next Use

Follow the project's normal entry as a later reader would. Repair a missing link
or explanation so the reader can find the method and its next action.
At relevant startup or reuse, compare changed conditions before another attempt;
a new chat, filename or release label alone leaves the precedent applicable.

Revise factual applicability when evidence changes. Proposed standing-rule changes
follow user confirmation. Keep temporary workarounds conditional; place corrections
outside frozen history and update the current pointer.

## Close The Knowledge Impact

Complete authorized owner and entry changes together. If another writer owns the
surface, return the finding and intended location through the existing handoff.
A summary-only request ends with the summary.
Use a fresh-context reuse check when the maintenance mechanism itself changes or
a real failure warrants it; routine notes use affected meaning/link checks.
