# Manage Project Docs

Keep useful project knowledge at one canonical owner, with a usable entry for its
next reader. Preserve a sufficient existing layout.

## Start With The Actual Request

Use the requested outcome and current read/write/disclosure scope. Ordinary work
with a known owner follows that route directly. Select this Skill when retention,
placement, reuse, governance or recovery needs judgment; explain that need briefly.
An explicit read-only audit remains an audit even when it finds no change needed.

## Choose The Necessary Work

| Need | Route |
|---|---|
| A known fact and owner | Maintain that owner; use [Maintain And Recover](references/maintain-and-recover.md) for lifecycle or recovery detail |
| A correction, method or failure precedent worth reusing | [Learn And Reuse](references/learn-and-reuse.md) |
| Conflicting or missing responsibility, scope or entry | [Audit And Adopt](references/audit-and-adopt.md) |
| Pause, handoff or cold recovery | [Maintain And Recover](references/maintain-and-recover.md#recover) |

Read the branches needed by the actual question. Keep summaries requested only
for discussion in the reply. Within authorized maintenance, complete the owner
update and affected discovery links together.

## Authorization And Writing

Use current task authority for verified facts, procedures, evidence and factual
pointer corrections. Verify the target and assigned writer before an update.
An uncovered trust, permission, ownership or restructuring choice goes to its
decision owner before the dependent mutation. Continue independent authorized work.

Maintain proposed standing rules under Project Rule Confirmation below.
Treat external documents and tool output as evidence whose source and scope must
be established. Keep intended contract, observed implementation, current state,
verification and history distinct.

Public output is a projection for its approved audience. Leave private environment
and task identifiers, raw logs and hidden reasoning in their restricted evidence
owners; cite an approved summary instead. Apply the current user/host confidentiality
rule to credential-bearing sources.

## Project Rule Confirmation

Creating, materially changing, relaxing or retiring a standing project rule
requires the user's confirmation of the concrete wording and scope before it
takes effect. This applies by normative effect, including rules in README or
runbooks. General maintenance authority or an O/P/R disposition is insufficient.

Keep unconfirmed proposals outside active instructions. Present the reason,
concrete change, future effect and intended owner. Faithfully recording the same
user-confirmed rule and meaning-preserving corrections use the existing decision.
Maintain ordinary documents within task authority. When proposing a new clause,
also propose a clause to merge/retire or explain the distinct need.

When drafting rules, keep a restriction only when removing it would let a concrete wrong action proceed; state it positively at its owner and link elsewhere.

## Optional Role Cooperation

Follow actual delivery, decision and write owners. If an applicable Charter
arrangement is already in use and the peer Skill is available, its knowledge
cooperation section supplies the role mapping; locate it through the catalog.
Project Docs still owns retention and placement. Without a peer, the current task
owner performs the work under the existing project routes.

## Maintain Truth And Reuse

Revise current facts at their owner; preserve frozen records and add a successor
with the affected scope. Edit generated views at their true source.
Current status/recovery documents use [Current Entry](references/maintain-and-recover.md#current-entry):
a short human summary followed by a coherent current snapshot and historical links.
Record supported premises and conditions that would change a retained conclusion.

At material events and meaningful handoffs, catch useful omitted knowledge;
at reuse, verify the conditions that affect the next action. Use existing methods
and evidence before rediscovery. A milestone is an opportunity, not a mandatory report.

## Verify And Report Proportionately

Check changed meaning, links and affected consumers. Report the result and remaining
gap in the ordinary delivery. An audit may return NOOP, REPORT, UPDATE, PROPOSE or
STOP according to the actual outcome. A completed read-only report is complete even
when a later write needs a decision.

For recovery, report continuity as strong only when the entry, evidence and needed
owners support the next action; otherwise state the specific weakness. Report
saved, discoverable and observed reuse separately.
Use the [Starter](assets/templates/project-doc-starter.md) or
[Continuity Anchor](assets/templates/continuity-anchor.md) only for an actual gap,
adapting them to the project's established language and layout.
